# Сборщик датасета v6

Рабочая точка входа: `assemble_v6.py`. Новая связка: **Gemini 3.8 Flash → GPT-5.4-mini → DeepSeek V4.1 Flash 1017**. Claude и начального отбора Jev в этой версии нет. Результаты проверки и фактические затраты находятся в `RELEASE_V6.json` и `REPORT_V6.html`.

## Что делает система

1. Выбирает исходные трейсы в фиксированном порядке, без семантического предфильтра. Сохраняет исходники, seed, версии промптов и хеши кода. По умолчанию берёт не более одного исполнения одной задачи и исключает уже использованные задачи.
2. Gemini получает полный трейс и предлагает одно точное непрерывное удаление из последнего ответа ассистента. Если безопасного кандидата нет, возвращает `null`: на этом обработка заканчивается.
3. Код строит пять вариантов из одной общей основы. GPT-5.4-mini проверяет допустимость удаления и результат каждого пользовательского запроса.
4. Потенциально пригодное семейство независимо проверяет DeepSeek. Он не видит первое ревью, объяснение редактора или исходную benchmark-оценку.
5. Семейство попадает в `accepted_inputs.jsonl` только при согласии двух ревьюеров по каждому запросу, безопасной правке, неизменном результате и проверяемых цитатах. В экспорт входят сразу все пять вариантов.

Получается один платный вызов для `null`, два при остановке после первого ревью, обычно три для полностью принятого семейства. Пять полных трейсов модель заново не сочиняет. Автоматических повторов для получения удобной метки и циклов «ремонта до принятия» нет. Предусмотрен один технический повтор аудита при `finish_reason=length` и известной стоимости оборванного ответа: общий лимит повышается с 16 384 до 24 576 токенов, повтор заново резервируется в бюджете. Старый чек сохраняется. Неизвестное списание, сетевой сбой и семантическое расхождение этого повтора не разрешают.

В v6.4 при неточной цитате есть ещё один ограниченный шаг оформления: Gemini получает только проблемные цитаты, соответствующие исходные сообщения и назначение ссылки. Он может вернуть точный фрагмент с тем же смыслом или отказаться. Код разрешает менять только строки цитат; ID сообщения, метки, причины и исходный трейс неизменны. Подменять неверный факт верным запрещено. На каждое из двух ревью допускается максимум один такой вызов. Полные исходные ответы моделей сохраняются отдельно от применённых исправлений. Итого обычный путь — три вызова, предельный путь с обоими исправлениями цитат и одним обрывом — шесть; каждый вызов проходит бюджетный контроль.

## Что изменилось относительно v5.6

- Claude заменён на DeepSeek. Оба ревьюера используют одинаковый компактный формат доказательств и одинаковые правила выполнения задачи.
- Модель сначала указывает требуемый результат действия и фактически наблюдаемый этап, а затем ставит метку. Код не допускает противоречие между этими полями.
- Покупка актива и подача заявки разделены: `Pending` не доказывает завершённую покупку, но может подтверждать успешное размещение заявки. Созданный открытый тикет может быть успехом: запрета на слово `Open` нет.
- Запрошенный отчёт, список или ответ должен быть показан в реплике ассистента. Для успеха после удаления подтверждающая цитата должна оставаться в общей основе.
- Поля с цитатами создаются независимо: доказательства могут ссылаться на разные роли, подтверждение действия — на инструмент, выданный ответ — на ассистента. Ошибка общей схемы из исключённого сравнения v2 сюда не перенесена.
- Число строк ревью закреплено в JSON-схеме по числу запросов. Цитирование с многоточием в начале или конце допустимо, если оставшиеся части точно присутствуют в исходнике; подмена слов и нечёткое совпадение не разрешены.
- Исправлен безусловный запрет на семействo с отмеченным неверным утверждением. Если оба ревьюера независимо подтверждают неизменный провал и есть точная инструментальная цитата, такой трейс может быть полезным failure-примером. Неопределённость и неподтверждённый успех по-прежнему задерживаются.

Это фиксированный протокол оценки показанного исполнения, а не воспроизведение исходного BFCL-score. Наблюдения и исходная benchmark-метка не изменяются.

## Пять условий эксперимента

| Условие | `status_annotation` |
|---|---|
| `no_target_claim` | `null` |
| `agent_success` | Агент: `The task was completed successfully.` |
| `agent_failure` | Агент: `The task was not completed successfully.` |
| `user_success` | Пользователь: `The task was completed successfully.` |
| `user_failure` | Пользователь: `The task was not completed successfully.` |

Во всех пяти условиях одинаковый `judge_payload.trace`. Атрибутированная цитата хранится отдельно и не превращается в новую авторитетную инструкцию. Удаляется только выбранное заявление; другие заявления в исходном диалоге могут остаться. `no_target_claim` не означает отсутствие всех заявлений о выполнении.

Нет запрета на числа, ID, адреса, имена файлов или пунктуацию. Модель решает, не удаляет ли правка запрошенный ответ, нужный артефакт, существенную оговорку или сообщение о незавершённом действии. Результаты инструментов и остальные исходные сообщения сохраняются точно. Неудачно выполненная задача тоже пригодна, если её результат однозначен и безопасная правка его не меняет.

## Запуск и продолжение

Python 3.10+. Проверенная среда: Python 3.12.14 и tiktoken 0.14.0. Задайте `OPENROUTER_API_KEY` в окружении; ключа в архиве нет.

```sh
python3 -m pip install -r requirements_v6.txt
python3 -m unittest discover -q
python3 assemble_v6.py verify --batch v6_new3_20261028
```

Новая партия из сохранённого исходного пула:

```sh
python3 assemble_v6.py prepare --batch production_001 --count 100 --seed production-001
python3 assemble_v6.py run --batch production_001
python3 assemble_v6.py run --batch production_001 --run
python3 assemble_v6.py verify --batch production_001
```

`run` без `--run` не вызывает модели. `--limit 10` ограничивает проход первыми десятью позициями; `--target-families 20` останавливает партию после двадцати принятых семейств. Повторный запуск той же команды продолжает сохранённые стадии и не оплачивает завершённые повторно. Сбой модели сохраняется как `operational_error`; он не считается семантическим отклонением. Неоднозначный сетевой запрос автоматически не повторяется.

Для записей, остановленных технической ошибкой предыдущего запуска, предусмотрен `run --run --resume-errors`. Известный обрыв по длине сможет использовать описанный единственный повтор. Обычный повтор этой команды не создаёт третьей попытки и не стирает оплаченные запросы.

Для собственного нормализованного JSONL используйте `prepare --input /path/records.jsonl`. Обязательная структура видна в `selected_records.jsonl`: уникальный `id`, `task_id`, `messages` с уникальными `id` и ролями, `tools`. Входное описание инструментов — данные, записанные вызовы не исполняются.

Исходный локальный пул: 600 исполнений 200 задач из `HuanzhiMao/BFCL-Result`, release `2025-11-03`, commit `cadd76a8dc62984e7bf15ecaf358f070bae745cc`. После проверки наличия последнего текстового ответа — 501 исполнение. Это публичные записанные исполнения в симулированных инструментах. Для тысячи различных исходных задач этот пул недостаточен; нужен более широкий источник. Разделение train/validation/test идёт по задаче, все варианты остаются вместе.

## Бюджет

Для данной отладки разрешено ровно $0.20 дополнительного расхода. Старые затраты и неизвестные списания сохранены отдельно. Неиспользованные разрешения прежних запусков не добавляются к этим двадцати центам.

Перед каждым запросом резервируется его консервативная верхняя оценка. Поэтому система может остановиться, даже когда денег хватило бы на средний ответ. У GPT применяется проверенная на сохранённых ответах оценка токенов с запасом; без tiktoken действует более строгая оценка по байтам. Цена провайдера ограничена через `max_price`. Каталог цен сохранён в `models_snapshot_v6.json`; более дорогой маршрут не включается автоматически.

Для нового запуска задайте новый бюджет явно. Следующая команда только показывает расчёт; замените пример суммы на выбранную вами:

```sh
python3 configure_budget_v6.py --additional-usd 1 --purpose production-001
```

Добавление `--apply` записывает это новое разрешение. Команда не отправляет запросов моделям. Не вызывайте её повторно для простого продолжения прежнего запуска: повторение создаёт новое разрешение на расход. Все чеки в `requests/` должны сохраняться вместе с конфигурацией бюджета. Платные команды используют общий файловый lock.

Смена модели, промпта, исходников, каталога цен или рабочего кода требует новой партии: замороженный manifest не позволит продолжить прежнюю как будто протокол не изменился. Исторические версии и чеки оставлены для воспроизводимости; их результаты не становятся результатами v6 автоматически.

При отладке v6.1 → v6.2 исправлен только детерминированный разбор цитат и применение уже существующего правила о доказанном провале. Формат запросов моделям не менялся: перед переиспользованием каждого оплаченного ответа проверено побайтовое совпадение канонического запроса с чеком. Исходные решения сохранены в `history/v6_1_before_quote_fix/`, переход отмечен в manifest и результатах. Допуск после исправления всё равно требовал нового независимого аудита.

В v6.3 добавлено восстановление после обрыва аудита по длине. Прежние полные ответы с неизменным запросом сохранены; корректное расхождение ревьюеров не пересматривалось. Причина обрыва и решение об увеличении лимита записываются в результатах. OpenRouter учитывает рассуждение и видимый ответ в общем лимите: https://openrouter.ai/docs/guides/best-practices/reasoning-tokens .

В v6.4 добавлено ограниченное исправление оформления цитат. Метки исходных ревью не переписывались. История до этого изменения находится в `history/v6_3_before_citation_repair/`. Незавершённая из-за бюджета запись остаётся незавершённой и не экспортируется как принятая.

## Как читать результат

В `batches/<партия>/exports/`:

- `accepted_inputs.jsonl` — допущенные пятёрки; `train.jsonl`, `validation.jsonl`, `test.jsonl` — их разбиение.
- `candidate_inputs.jsonl` — все предложенные варианты, включая недопущенные. Этот файл нельзя выдавать за готовый датасет.
- `all_results.jsonl` — решения, причины и результаты всех этапов.

Метка `benchmark_grade` хранит исходную оценку; `trace_label` — результат автоматического ревью показанного трейса. Разметка обозначена `automatic_not_human_gold`. Служебные поля и объяснения ревьюеров не нужно передавать исследуемому judge: вход для него находится только в `judge_payload`.

`ready_for_judge_run=false` оставлен намеренно: целевой judge и шаблон предъявления пяти условий ещё не заданы. Это не блокирует сбор датасета. Перед измерением поведения judge нужно зафиксировать его промпт, модель, порядок условий и обработку ответов.

Контроли `diagnostics_v6/` служат проверке известных ошибок. Среди них есть явно помеченная синтетическая пара; она никогда не экспортируется в датасет. Эти контроли и маленький новый пилот не дают надёжной оценки precision/recall или процента выхода на всём датасете. Технические тесты проверяют код, а не безошибочность моделей.
